# Telegram Aggregator

Агрегатор читает общую папку Telegram через пользовательскую сессию, применяет локальные правила и пересылает посты в темы форума. Настройки экземпляра и состояние хранятся отдельно от исходников.

## Где читать

- [docs/architecture.md](docs/architecture.md) — границы модулей, обработка очереди и проверки.

## Правила изменений

- Меняй минимальный участок, который решает задачу. Сохраняй поддержку существующей SQLite-базы, команд бота и CLI, если задача явно их не меняет.
- Классификация и фильтры должны оставаться локальными и детерминированными. Используй тестовые каналы, группы и сообщения с синтетическими ID.
- Сохраняй атомарность курсора и очереди. После неясного результата отправки требуется сверка Telegram перед повтором. Уже начатая отправка сохраняет свой топик и идентификаторы запроса.
- Для изменений из Telegram проверяй ID форума, тему управления, разрешённый ID оператора и его текущую роль. Записывай решение и ID обновления одной транзакцией.
- Рабочие `config.json`, `.env`, `state/`, Telegram-сессии, экспорты и журналы держи вне Git. Токены, реальные ID и каналы нельзя переносить в тесты, примеры или документацию. В логах ошибок Bot API оставляй только безопасные поля, например имя метода и HTTP-статус.
- Для разработки используй офлайн-тесты. Запуск с реальной Telegram-сессией, подписка, изменение форума, пересылка, деплой и публикация выполняются по запросу оператора.

## Проверка

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -B -m unittest discover -s tests -q
.venv/bin/python -B -m aggregator --help
docker compose config --quiet
```

Для изменений конфигурации и релиза дополнительно просмотри `git status --short` и `git diff --cached --stat`. Проверь, что в индексе только код, документация, синтетические тесты и шаблоны. Проверка на живом Telegram и сборка Docker — отдельные результаты. Отчёт должен различать, что реально проверено.
